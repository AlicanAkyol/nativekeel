SonarQube

React Native and Expo checks, inside SonarQube

SonarQube reads your JavaScript, Kotlin and Swift, but it does not know that Xcode 27 will not launch an app without UIScene, that Google Play hides apps with an old target SDK, or that a library stops the iOS build on React Native 0.87. NativeKeel does, and it can hand those findings to SonarQube, so they sit in the same project, the same dashboard and the same quality gate as everything else.

What it looks like

A small sample app, analyzed by SonarQube Community Build 26.10. SonarQube's own analysis found nothing in it. With NativeKeel's report imported, the same project shows 10 issues, and its Security and Reliability ratings drop to E: an AWS key shipped in the app, a target SDK that hides the app on Google Play, a committed signing password.

The quality gate in this screenshot still passes because SonarQube's default gate looks at new code, and this was the project's first analysis. From the next analysis on, new NativeKeel findings count like any other new issue.

Two lines in your pipeline

npx nativekeel --sonar nativekeel-sonar.json --fail-on never
sonar-scanner -Dsonar.externalIssuesReportPaths=nativekeel-sonar.json

Run both from the folder SonarQube analyzes (sonar.projectBaseDir): file paths in the report are written relative to it. Keep package.json, ios/ and android/ inside sonar.sources, because SonarQube attaches each issue to a file it indexed.

With GitHub Actions

steps:
  - uses: actions/checkout@v5
  - uses: AlicanAkyol/nativekeel@v0
    with:
      sonar: nativekeel-sonar.json
      fail-on: never        # let the SonarQube quality gate decide
  - uses: SonarSource/sonarqube-scan-action@v8
    env:
      SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
      SONAR_HOST_URL: ${{ secrets.SONAR_HOST_URL }}
    with:
      args: -Dsonar.externalIssuesReportPaths=nativekeel-sonar.json

critical · high · medium · lowBlocker · High · Medium · Low (Blocker · Critical · Major · Minor in Standard Experience)

Each issue points to the file and line NativeKeel found, or to the package.json line that declares the package. Rules show up as external_nativekeel:<check>. Accepted findings are managed in NativeKeel's .nativekeel.json (each with a reason), since SonarQube does not manage external rules in quality profiles.

Tested on SonarQube Community Build 26.10 with the generic issue import format (SonarQube Server 10.3 and later): all findings of a sample app arrived with their file, line, software quality and severity.

Why it fits teams already on SonarQube

  • No new dashboard to watch. Mobile findings live where your team already looks.
  • Your code stays where it is. NativeKeel runs in your pipeline and writes a JSON file; only package names go to npm and React Native Directory (--offline sends nothing).
  • Free and MIT licensed, no account, no dependencies.
