What could go wrong?

Credentials escape the app

Tokens and wallet secrets passed to telemetry, passwords embedded in URLs, secrets bundled in the app, unsafe storage and sensitive clipboard use.

Keys added at build time

An EXPO_PUBLIC_ value set in EAS or a CI secret is compiled into the app without ever appearing in the repository. NativeKeel opens the built APK, AAB or IPA (or the bundle Gradle wrote) and scans the JavaScript bundle inside it, including Hermes bytecode: npx nativekeel --artifact app-release.apk.

API checks the client gets wrong

URLs trusted after a text comparison, the mistake behind Zulip's CVE-2022-35962: startsWith('https://site.com') also accepts site.com.attacker.dev, includes('site.com') accepts any URL containing it. Reported where the check decides trust (a WebView allowlist, an origin check, code that sends credentials). Also: isPremium: true, a role or credits written to Firestore or Supabase by the app itself, and a global axios interceptor that adds the login token to calls to other sites.

CI that hands out your store keys

A pull_request_target workflow runs with the repository's secrets and a token that can write to it, for pull requests from any fork. If it checks out the pull request and then installs, builds or tests it, the fork's author runs their own code with your EXPO_TOKEN, App Store Connect or Play credentials. Jellyfin's iOS app was exposed this way (GHSA-7qhm-2m45-7fmh): NativeKeel reports the workflow before the fix and nothing after it. Jobs limited to the repository's own branches, or behind an approval environment (directly or through needs:), are left alone.

Another user reaches private data

Open Firebase rules, overly broad writes, reads any signed-in user can make on people or private records (users, messages, orders, every file in Cloud Storage), Supabase tables of people with email or phone columns that anyone can read, storage buckets with private names (receipts, documents, kyc) created public, and supported Supabase RLS policy mistakes. Deployed permissions and cross-account isolation still need runtime verification.

Untrusted data becomes code

WebView messages or fetched response bodies reaching eval/Function; traced text input or navigation values concatenated into SQLite query text.

Login or file sharing loses protection

OAuth code flows with PKCE explicitly disabled, implicit redirect tokens, and referenced FileProvider paths that cover entire private directories.

Databases visible in the Files app

iOS file sharing (UIFileSharingEnabled) shows the app's Documents folder in Finder and the Files app. react-native-mmkv, expo-sqlite and Realm store their data there by default on iOS, so an unencrypted database can be copied out by anyone holding the unlocked phone.

Biometric unlock that guards nothing

Face ID, Touch ID or fingerprint prompts whose success is only a yes/no in JavaScript, with no keychain or keystore secret bound to biometrics in JS or native code. On a jailbroken or rooted device the answer can be faked; the fix is to keep the secret behind biometric access control.

Native Android entry points and file paths

Six additional checks follow Java/Kotlin source: archive entry names reaching file writes, incoming nested Intents launched by an exported Activity, caller-selected WebView URLs, Intent text in local SQL, and caller-selected file reads or writes. Intent findings require an explicitly exported manifest entry without a declared permission and a matching source class; literal Gradle namespaces are supported. Merely having an exported Activity is not one of these flow findings.

Android 14 adds ZIP entry validation for apps targeting API 34+; Android 16 adds Intent launch protection. Findings describe these mitigations and ask for tests on supported devices. A file read is not automatically reported as exfiltration, and loading a URL is not automatically reported as native code execution.

A useful finding explains the attack conditions

Example: a WebView message reaches eval.

Evidence: the message value reaches a code-execution call, with file and line references.

Possible damage: page-controlled JavaScript runs in the app runtime.

Prerequisite: an attacker must control the page or inject script into it. This is not proof that your production page is compromised.

Fix and verification: use a fixed command allowlist with validated JSON; test locally with a harmless canary and confirm it is never executed.

Evidence over a reassuring score

The report separates static evidence, attacker prerequisites and verification steps. It includes existing TLS, dependency, secret and planted-malware checks. Export HTML for review, JSON for automation or SARIF for code scanning. Coding agents can call security_audit over MCP.

No matching findings is not proof of security. These checks do not run your app, test a deployed backend, analyze every data flow or certify MASVS compliance. The new flow checks follow short local aliases; complex validation, cross-file flows and skipped files can hide problems. Runtime and account A/B tests remain necessary.

How the new checks were verified

Each rule has positive and negative fixtures. A read-only pass over 922 repositories produced 13 source matches in 11 repositories after exclusions for public map identifiers, server/web code and cache-only sharing. These are review candidates, not confirmed breaches. No corpus application or malicious sample was executed.

The six native checks have positive and negative fixtures and CLI/MCP/report integration coverage. A read-only pass over 922 repositories produced no matching native findings. Guards, complex branches and unknown transformations may stop analysis; no match is not a passed security control. These new native flows currently cover Android, not iOS native flows, release binaries or deployed services.

Checked against vulnerabilities other people found. Ten published cases in scope for static analysis (GitHub security advisories of React Native apps, and commits in React Native repositories that removed a leaked key, scanned at the commit before the fix): NativeKeel found 5 before 0.1.107 and 7 after. It finds Rocket.Chat's exported reply receiver (GHSA-gwg8-fvp7-mp2x) and no longer does on the fixed release. It misses Zulip's link check done with a string prefix (CVE-2022-35962), which needs data-flow analysis, and two app-specific API keys whose name and format look like public keys.

The built-app scan was checked on Hermes bytecode compiled with the React Native 0.87.1 compiler: keys stored back to back with other strings and keys inside non-ASCII (UTF-16) strings are found. Only key formats with a distinctive prefix are matched inside bytecode (for OpenAI keys, also the marker every key carries), after a first version matched CSS names such as mask-image; built bundles of 20 open-source apps produced no findings.
